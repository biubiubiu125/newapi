# NewAPI 上游同步收尾设计

## 目标

在不覆盖商业二开业务行为的前提下，完成当前 NewAPI 分支的上游同步收尾：移除未使用的 `web/classic/`，吸收适用的上游通用改进，补齐 `TaskPublicAddress` 的真实任务产物链路，修复并归类验证问题，最后形成可审计的本地提交。

## 当前基线

- 本地分支：`main`
- 本地基线提交：`d7528a12363a2a28fb421347b60ecfc7db7cb686`
- 上游基线：`upstream/main`，当前提交为 `0ed497f066a68613375124303ef54f220267b334`
- 本地相对上游落后 70 个提交。
- 当前已有未提交的第一阶段改动，不能丢弃或用上游整树覆盖。

## 设计边界

### 保留的二开行为

继续保护当前实际使用的图片任务生命周期与结算、支付、订阅、推荐、提现、渠道故障转移、计费、权限/状态、部署配置和新版 `web/` 前端。保护范围按实际调用链判断，不把所有本地差异都视为必须保留。

### 上游同步方式

不直接执行整树 `ours`/`theirs` 解决，也不把本地修复描述成完成上游合并。逐项检查上游提交，按以下四类处理：

1. 删除已废弃且未使用的本地代码；
2. 直接吸收不改变二开业务语义的通用修复；
3. 沿路由、控制器、服务、模型、Relay、前端和测试手工融合有交集的改动；
4. 对会改变现有收费、结算、权限或外部接口语义的改动保留为明确的待决项，不隐式替换。

## 实施方案

### 1. `web/classic/` 清理

先扫描构建、嵌入、CI、发布、路由、部署和测试引用，保存删除前的文件清单；确认当前运行只依赖 `web/dist` 后，将 `web/classic/` 整体移入系统回收站。保留数据库中旧 `theme.frontend` 的迁移兼容能力，但运行时不再切换到 classic，并同步修正文档和兼容测试。

### 2. 上游提交分组同步

按影响范围处理上游 70 个提交：

- 先处理数据库初始化、迁移兼容、锁与并发、连接池、响应头超时等低冲突稳定性修复；
- 再处理 Relay/协议转换、工具调用、推理字段、usage 与计费完整性；
- 再处理任务插件、订阅/充值/钱包、授权、OAuth 等业务链路，逐条检查本地二开交集；
- 最后处理前端、构建、依赖、文档和测试。

每组完成后运行对应包测试和差异检查，避免一次性堆积无法定位的冲突。依赖升级只在上游代码确实要求时采纳。

### 3. `TaskPublicAddress` 真实链路

沿现有任务创建、状态查询、结果保存、结果下载和 OpenAPI 文档追踪数据流。配置只接受绝对 HTTP(S) 地址；任务产物 URL 必须绑定任务 ID 和产物 key 的签名能力，下载端点必须校验签名、任务归属、产物 key 和过期策略。前端系统设置、后端校验、任务服务、路由和测试保持同一命名。

如果当前分支不存在对应的任务产物下载端点，则不保留无法被业务调用的孤立 helper；应先采用上游完整接口或按本地任务模型手工融合，再保留配置功能。

### 4. 测试和构建

对已知失败先按测试名复现并追踪根因，再决定修复或标记为基线/环境问题。验收至少包括：

- 受影响 Go 包的定向测试；
- 根模块编译与相关 Go 测试；
- `relaykit` 独立构建；
- 前端受影响测试、`bun run typecheck`、相关文件 lint 和生产构建；
- `git diff --check`、经典前端引用扫描和最终变更清单审查。

### 5. 交付

完成最终差异审查后提交本地 Git，提交信息按变更阶段拆分且不包含密钥、构建产物、抓包或导出数据。不上推远端、不直接部署生产；生产部署另行保存 `.env`/`docker-compose.yml`，确认 PostgreSQL、容器和回滚路径后再执行。

## 验收标准

- `web/classic/` 不再存在，且不影响新版前端构建、嵌入、路由和发布。
- 旧主题配置不会重新启用 classic；已有数据库值迁移行为明确且文档一致。
- 上游适用修复已按提交或提交组落地，并有本地二开保护说明。
- `TaskPublicAddress` 从配置到真实任务产物访问链路可用，失败输入和权限边界有测试。
- 所有可复现的本次变更失败均已修复；环境/基线失败有明确证据和说明。
- 最终提交可回滚，工作区无未预期文件。
